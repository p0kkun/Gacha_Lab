# 動画ファイル配置場所の比較: S3 vs public/

## 概要

動画ファイルを配置する場所として、**`public/`ディレクトリ**と**Amazon S3**の2つの選択肢があります。それぞれのメリット・デメリットを比較します。

## 比較表

| 項目 | `public/`ディレクトリ | Amazon S3 |
|------|---------------------|-----------|
| **設定の簡単さ** | ✅ 設定不要（自動） | ❌ 追加設定が必要 |
| **デプロイサイズ** | ❌ 大きくなる（Gitリポジトリに含まれる） | ✅ 小さい（Gitリポジトリに含まれない） |
| **ファイルサイズ制限** | ⚠️ 制限あり（Git/デプロイの制約） | ✅ 制限なし（S3の制限のみ） |
| **更新の容易さ** | ❌ デプロイが必要 | ✅ 直接アップロード可能 |
| **コスト** | ✅ 無料（Amplifyに含まれる） | ⚠️ S3ストレージ料金 + 転送料金 |
| **キャッシュ制御** | ⚠️ Amplifyのデフォルト設定 | ✅ 細かい制御が可能 |
| **管理画面からのアップロード** | ❌ 難しい | ✅ 容易（S3への直接アップロード） |
| **バージョン管理** | ✅ Gitで管理 | ❌ 別途管理が必要 |

## 1. `public/`ディレクトリ（現在の構成）

### メリット

1. **設定が簡単**
   - 追加設定不要
   - Next.jsが自動的に静的ファイルとして配信
   - AWS Amplifyが自動的にCloudFrontでキャッシュ

2. **コストがかからない**
   - Amplifyのホスティングに含まれる
   - 追加のストレージ料金なし

3. **バージョン管理が容易**
   - Gitで管理できる
   - 変更履歴を追跡可能

4. **デプロイが自動化**
   - コードと一緒にデプロイされる
   - 一貫性が保たれる

### デメリット

1. **デプロイサイズが大きくなる**
   - 動画ファイルがGitリポジトリに含まれる
   - デプロイ時間が長くなる可能性
   - GitHub/GitLabのファイルサイズ制限（通常100MB/ファイル）

2. **更新が面倒**
   - 動画を更新するにはコードをデプロイする必要がある
   - 管理画面からの直接アップロードが難しい

3. **ファイルサイズの制約**
   - 大きな動画ファイル（100MB以上）はGitで管理しにくい
   - リポジトリのサイズが大きくなる

4. **キャッシュ制御の制約**
   - Amplifyのデフォルト設定に依存
   - 動画専用の最適化設定が難しい

### 推奨される用途

- ✅ **小〜中サイズの動画ファイル**（10MB以下）
- ✅ **変更頻度が低い動画**
- ✅ **動画ファイル数が少ない**（10個以下）
- ✅ **シンプルな構成で運用したい場合**

## 2. Amazon S3（推奨：大容量・頻繁な更新）

### メリット

1. **ファイルサイズ制限なし**
   - 大容量動画ファイル（100MB以上）も問題なし
   - 5GB/ファイルまで対応（それ以上も可能）

2. **更新が容易**
   - 管理画面から直接アップロード可能
   - デプロイ不要で即座に反映

3. **Gitリポジトリが軽量**
   - 動画ファイルがGitに含まれない
   - デプロイが高速

4. **細かいキャッシュ制御**
   - CloudFrontのキャッシュポリシーを細かく設定可能
   - 動画専用の最適化設定

5. **スケーラビリティ**
   - 大量の動画ファイルに対応
   - ストレージ容量の制約が少ない

### デメリット

1. **追加設定が必要**
   - S3バケットの作成
   - CloudFrontディストリビューションの設定
   - IAMポリシーの設定

2. **コストが発生**
   - S3ストレージ料金: 約$0.023/GB/月（東京リージョン）
   - CloudFront転送料金: 約$0.085/GB（最初の10TB）
   - ただし、小規模な運用では無料枠内の可能性も

3. **バージョン管理が別途必要**
   - Gitで管理されない
   - S3のバージョニング機能を使用する必要がある

4. **セキュリティ設定**
   - バケットポリシーの適切な設定が必要
   - アクセス制御の管理が必要

### 推奨される用途

- ✅ **大容量動画ファイル**（100MB以上）
- ✅ **動画ファイル数が多い**（10個以上）
- ✅ **頻繁に動画を更新する**
- ✅ **管理画面から動画をアップロードしたい**
- ✅ **動画専用の最適化設定が必要**

## 3. 推奨構成（プロジェクトの規模による）

### 小規模プロジェクト（現在の構成）

**`public/`ディレクトリを使用**

```
app/
└── public/
    └── videos/
        ├── item1.mp4  (5-10MB)
        ├── item2.mp4
        └── ...
```

**理由:**
- 設定が簡単
- コストがかからない
- 動画ファイル数が少ない
- 変更頻度が低い

### 中〜大規模プロジェクト

**S3 + CloudFrontを使用**

```
S3バケット: gacha-lab-videos
├── videos/
│   ├── item1.mp4
│   ├── item2.mp4
│   └── ...
└── CloudFront: https://[distribution-id].cloudfront.net/videos/
```

**理由:**
- 大容量動画に対応
- 管理画面からのアップロードが容易
- Gitリポジトリが軽量
- スケーラビリティが高い

## 4. 移行の判断基準

### `public/`ディレクトリからS3への移行を検討すべき場合

1. **動画ファイルの合計サイズが100MBを超える**
2. **動画ファイル数が10個以上**
3. **管理画面から動画をアップロードしたい**
4. **動画ファイルを頻繁に更新する**
5. **大容量動画（100MB以上）を使用する**

### 現在の構成を維持すべき場合

1. **動画ファイルの合計サイズが100MB以下**
2. **動画ファイル数が10個以下**
3. **動画の更新頻度が低い**
4. **シンプルな構成で運用したい**
5. **追加のコストを避けたい**

## 5. ハイブリッド構成（将来的な選択肢）

小さい動画は`public/`、大きい動画はS3に配置する構成も可能：

```typescript
// 動画URLの生成ロジック
function getVideoUrl(videoUrl: string): string {
  // S3の動画（URLがhttps://で始まる場合）
  if (videoUrl.startsWith('https://')) {
    return videoUrl;
  }
  
  // public/の動画（/videos/で始まる場合）
  if (videoUrl.startsWith('/videos/')) {
    return videoUrl;
  }
  
  // デフォルト
  return `/videos/${videoUrl}`;
}
```

## 6. 現在のプロジェクトでの推奨

### 現時点での推奨: `public/`ディレクトリを継続

**理由:**
1. 動画ファイル数が少ない（現在は`item1.mp4`のみ）
2. ファイルサイズが小さい想定
3. 設定が簡単で運用コストが低い
4. AWS Amplifyの自動CloudFront設定で十分

### 将来的にS3への移行を検討すべきタイミング

1. 動画ファイル数が10個を超えた
2. 動画ファイルの合計サイズが100MBを超えた
3. 管理画面から動画をアップロードする機能を実装する
4. 大容量動画（100MB以上）を使用する必要が出た

## 7. S3移行時の実装手順（参考）

### ステップ1: S3バケットの作成

```bash
aws s3 mb s3://gacha-lab-videos --region ap-northeast-1
```

### ステップ2: CloudFrontディストリビューションの作成

- オリジン: S3バケット
- キャッシュポリシー: 動画最適化ポリシー
- パス: `/videos/*`

### ステップ3: 環境変数の設定

```env
NEXT_PUBLIC_CLOUDFRONT_VIDEO_URL=https://[distribution-id].cloudfront.net
```

### ステップ4: コードの更新

```typescript
// 動画URLの生成
const videoUrl = item.videoUrl.startsWith('https://')
  ? item.videoUrl
  : `${process.env.NEXT_PUBLIC_CLOUDFRONT_VIDEO_URL}${item.videoUrl}`;
```

## 結論

### 現在のプロジェクト: `public/`ディレクトリが理想的

- ✅ 設定が簡単
- ✅ コストがかからない
- ✅ 現在の規模に適している

### 将来的にS3を検討すべき場合

- 動画ファイル数が増えた
- 大容量動画を使用する
- 管理画面から動画をアップロードしたい

---

**推奨**: 現時点では`public/videos/`ディレクトリを使用し、将来的に必要に応じてS3への移行を検討する。
